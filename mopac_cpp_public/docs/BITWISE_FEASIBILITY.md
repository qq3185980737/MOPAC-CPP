# 能否把 C++ 版优化到「所有分支 16 进制逐位一致」？

> 分析对象：`D:\test_rep\mopac_cpp_public`（MSVC 2022 / C++17 / 静态 MKL 2025）
> 对照基准：`D:\mopac\mopac-archive\2016_MOPAC2016\x64\Release\MOPAC2016.exe`
> （Intel ifx + 静态 MKL 2025，见 §2 依赖分析）
> 结论先行：**做不到「所有分支 16 进制逐位一致」。**
> 可做到、也建议追求的是：**整数/文本/控制流分支逐位一致（已达成）**，
> 以及**打印到 5 位小数的数值一致（当前 140~176 / 144~188 行，剩余仅运行时量与
> 1e-6~1e-9 级噪声）**；原始 double 的逐位一致在“不同编译器 + 黑盒基准程序”
> 前提下不可达。

---

## 1. 当前还剩哪些差异（实测）

| 类别 | 实测例子 | 量级 |
|---|---|---|
| 时间戳/墙钟/CPU 时间 | `Sun Oct 25 …`、`WALL-CLOCK TIME 0.016 vs 0.000` | 每次运行都不同 |
| 极化率 α（静态） | 官方 9.67480，C++ 9.67479 | 1.0e-6 相对 |

## 2. 逐项根因分析（带实测证据）

### 2.1 编译器代码生成差异（主因，可测）

同一段 `alphaf` 代码、**完全相同的输入**（C++ 导出的 `alphaf.in`），分别用：

- Fortran ifx 默认选项编译的 harness；
- Fortran ifx `/O2 /fp:strict /Qfma-` 编译的 harness；
- 我们的 C++ `alphaf()`；

对最终 3×3 α 矩阵的 9 个 double 取位比较（`compare_dump.py`）：

| 对比 | 不一致项 | 最大相对差 | 说明 |
|---|---|---|---|
| C++ vs ifx 默认 | 8/9 | 7.8e-7（近零元） | 大对角元也差 1 ulp |
| C++ vs ifx 严格无 FMA | 5/9 | 1.2e-6（近零元） | **大对角元已经逐位相等** |
| ifx 默认 vs ifx 严格 | 9/9 | 3.9e-7 | 仅编译选项不同就改变全部结果 |

结论：
- Fortran 默认优化会做 **FMA 收缩 / 向量化**，改变每一步的舍入；
- 我们的 C++（MSVC 默认 `/fp:precise`、SSE2 标量）对应的是“严格标量”语义，
  所以在严格 Fortran 下大对角元可以逐位一致 —— **说明代数公式本身没错**；
- 但近零分量由大数相消得到，1 ulp 的中间差异被放大成 1e-6 相对差，
  这类量在默认 Fortran 下必然不同；
- 黑盒的官方 exe 用的是哪种选项无法从源码层控制，因此**无法从 C++ 侧
  复现其逐条指令的舍入序列**。

### 2.2 数学库（本次实测：不是主因，但不能排除）

用 ifx 与 MSVC 分别计算 12 组典型值的 `exp/log/sin/cos/atan2/pow` 并取位：

```
total {exp:12, log:12, sin:12, cos:12, atan2:12, pow:12}
differing {}          ← 全部逐位相同
```

十进制输入解析也实测逐位一致（`0.757`、`3.141592653589793` 的 IEEE 位相同）。

所以在本机这对工具链上，**libm/strtod 不是当前差异的来源**（Windows 上
ifx 静态运行库与 UCRT 在这些点重合）。但不能据此断言“所有参数都一致”：
`pow/exp` 在极端参数、次正规数、范围缩减边界仍可能差 1 ulp；一旦出现在
积分/阻尼函数里，就会进入 §2.1 的放大链。

### 2.3 数值库（MKL/LAPACK）版本与归约顺序

- 两个 exe 都静态链接了 **oneAPI MKL 2025**（dumpbin：官方仅依赖
  `libiomp5md.dll`，MKL 在 exe 内；字符串同样含
  “oneAPI Math Kernel Library Version”），版本族一致；
- 但静态嵌入的**具体补丁版本/构建路径**无法核对；LAPACK `dsyevd`、
  BLAS `dgemm` 的向量化归约顺序与补丁版本相关，最后 1~2 bit 可能不同；
- 线程数实测：官方 α 在 `OMP_NUM_THREADS=1` 与 `=4` 下**完全相同**，
  说明当前 α 打印差异不是线程归约造成的（我们构建也强制 1 线程）；
- 结论：MKL 不是“必然不同”，但**不可验证**，且一旦不同就会污染整个
  SCF/响应链。

### 2.4 迭代放大与分支翻转（“所有分支”不可达的直接原因）

SCF、几何优化、响应迭代都是**非线性、带阈值分支**的过程：

```
Fock(P) → 对角化 → P' → 收敛判据 pl<scrcrt … → 重复
```

- 1 ulp 的积分/Fock 差异 → 密度差 ~1e-12 → 下一轮 Fock 再放大；
- 一旦差值跨过判据（`scfcrt`、`gnorm`、线搜索、简并排序、平局比较），
  **分支走向就会不同**，输出结构随之变化；
- 已观测到的分支翻转：`MOLECULAR DIMENSIONS` 的三行排序（H2–O1 与
  O1–H2 互换）——完全由 3e-9 的坐标噪声决定；
- 偶极近零分量的 `+0.000/-0.000` 符号也由求和顺序决定。

因此“所有分支逐位一致”在逻辑上就要求“所有浮点比较前的值逐位一致”，
这与 §2.1 的编译器差异矛盾。

### 2.5 运行时依赖（不可消除）

- 时间戳、WALL-CLOCK/CPU/TOTAL JOB TIME 是**运行时刻**，两次运行必然不同；
- MOPAC 的 `DRC/GRID/PATH` 等分支里存在“剩余时间 tleft / second(2) − time0”
  的运行时判据，同一输入在不同机器/负载下会走不同分支；
- 这部分与实现无关，任何“逐位一致”承诺都必须排除。

### 2.6 移植实现中的残余代数/求和顺序差异（可减小，不能归零）

- `alphaf` 紧约束下大对角元已逐位相等，但 0.055 这类小量仍差 1 ulp，
  说明某些循环的求和次序/表达式分组与 Fortran 不完全相同；
- `gamma` 的 2.2e-5 相对差明显大于 1 ulp，属于**实现细节**（平均/置换
  累加顺序或某项展开次序），可以靠对照 Fortran 逐行修正来缩小；
- 坐标 3e-9 不是 libm 问题（§2.2），而是 C++ 几何路径多走了一次
  内部坐标↔笛卡尔转换/三角函数，可在纯笛卡尔输入分支直接使用原始坐标来消除。

这类问题**可以修到“打印 5 位小数一致”甚至局部逐位一致**，但无法改变
§2.1/§2.4 的跨编译器结论。

## 3. 分层结论：哪些“逐位一致”可达？

| 层级 | 目标 | 可达性 | 现状 |
|---|---|---|---|
| L0 | 整数/索引/字符串/控制流（非浮点分支） | ✅ 可达 | 已逐位/逐字节一致 |
| L1 | `.out/.arc` 文本行（排除时间行） | ⚠️ 接近 | 140~176/144~188；剩余是 1e-6~3e-9 数值行 |
| L2 | 打印数值 5 位小数一致 | ✅ 基本可达 | 仅 α/γ/坐标/符号/排序几行待修 |
| L3 | 原始 double 位级一致（局部子程序） | ⚠️ 有条件 | 严格标量 Fortran 下 α 大对角元已逐位一致 |
| L4 | 全程序所有分支原始位级一致（vs 官方 exe） | ❌ 不可达 | 编译器/库/迭代放大/时间分支 |
| L5 | 同一 C++ 二进制两次运行位级一致 | ✅ 可达 | 除时间行外完全确定（已无随机源） |

---

## 4. 如果一定要把 L4 推到极限，可行的工程手段

1. **双方都用严格标量 FP**：
   - C++：`/fp:strict`，禁用 FMA/自动向量化（`/arch:SSE2`、`/Qvec-` 等价）；
   - Fortran 参照：`/fp:strict /Qfma-`；
   - 但不掌握官方 exe 的编译选项，无法保证一致 → 只能用于“自建 Fortran
     对照版”验证子程序，而非对比官方 exe。
2. **锁定数值库**：同 MKL 版本、单线程、禁用并行归约；记录 `dumpbin` 依赖。
3. **消除 libm 依赖**：把 `exp/pow/sin/cos` 换成自己实现的确定性算法
   （或固定 libm 版本），避免极端参数下 1 ulp 漂移。
4. **手写 Fortran 内建归约的次序**：`SUM/dot_product` 在 Fortran 端可能被
   向量化，C++ 需按相同分组累加。
5. **逐子程序 harness 验证**：像 `alphaf` 这样导出同一份输入、位比较，
   把残差压到 1~2 ulp；这能证明“算法实现正确”，但不能让整程序对官方
   黑盒 exe 位级相等。

---

## 5. 建议的验收标准（务实）

1. **文本级**：`.out/.arc` 除时间行外逐字节一致（当前差距仅几行数值噪声，
   可继续修到接近 100%）；
2. **数值级**：所有打印到 5 位小数的量一致；原始 double 相对误差
   ≤1e-12（能量）/≤1e-6（响应量）；
3. **确定性**：同一 C++ 二进制重复运行，除时间行外字节一致；
4. 不建议把“所有分支 16 进制一致”作为验收条件 —— 它与“参照物是另一套
   编译器/库构建的二进制”这一前提不可兼容。

---

## 6. 一句话总结

> **可以**把整数/文本/控制流以及打印值修到一致，**也可以**在严格标量
> 编译下让局部子程序的原始 double 位级一致；但**不可能**让整个程序
> 相对官方 exe “所有分支 16 进制逐位一致”——根因是 ifx vs MSVC 的
> FMA/向量化代码生成差异（实测仅切换 ifx 严格选项就改变 9/9 个 α 值）、
> 迭代与阈值分支对 ulp 的放大（已观测到维度排序翻转）、以及时间/时钟
> 类运行时分支。这与 C++ 移植质量无关，是跨工具链可复现性的理论边界。

## 7. 专项：α/γ 的 1e-5 级残差（2026-10-25 追查结论）

对 POLAR 输出最后的两处确定性数值差（α 9.67480 vs 9.67479；γ
49.43625 vs 49.43734）做了专项排查：

| 假设 | 实验 | 结果 |
|---|---|---|
| SCF 收敛不足 | 加 `SCFCRT=1D-10` | 两侧值不变，α 差仍 1e-5 |
| POLAR 迭代截断 | `POLAR(ATOL/BTOL=1D-9, MAXIT=300/1000)` | 两侧同步移动，差不变 |
| 常数/参数错 | 核对 a0、polvol(99/100)、原子 polvol | 完全一致 |
| ngamtg 公式/表/记录号错 | 逐行核对 polar.F90:2848-3017 | 一致（9 分量、/5、DAF 偏移、fhpatn） |
| 数学库/解析 | ifx vs MSVC 位比较 | 采样逐位相同 |

机理：α 是一阶、γ 是三阶响应缩并；同一份输入下，α 大对角元在
ifx 严格标量下可与 C++ 逐位相等，但相消得到的近零分量放大了 ULP 差
（相对 1e-6）；γ 的 27 个乘积项把该差异进一步放大到 1e-3 绝对
（大分量；小分量几乎逐位相同），与实验一致。

因此该残差**不是公式/排版错误，无法通过改打印或调容差修复**；
它只是 §1–§2 跨编译器 ULP 差异在响应链上的具体表现。
`ngamtg()` 内保留了 env 门控的 `NGAMTG_DEBUG` 诊断（默认关闭），
便于以后继续观察。
